Risk intelligence for the people behind packages.

MaintainerWatch statically analyses public registry metadata and bounded package archives, resolves maintainer identities, and computes explainable signals for maintainer-level supply-chain risk across npm, PyPI, crates.io and Maven Central. It never executes package code in the analyst process.

    Add it to CI in five minutes

    The action checks only dependency manifest changes against the latest compact index. It never downloads or executes package code. Start advisory, then raise the threshold after local validation. 

    name: MaintainerWatch
on: pull_request
permissions:
  contents: read
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: ovidiurg/maintainerwatch@main
        with:
          index-url: https://github.com/ovidiurg/maintainerwatch/releases/latest/download/maintainerwatch-index.json
          base-ref: origin/${{ github.base_ref }}
          fail-on: none
          comment: "true"
          upload-sarif: "true"

    Pin the action to a commit or release tag for production. Do not use pull_request_target for untrusted pull requests. Full setup, SARIF and comment behaviour are in the PR/CI guide and expiring waivers.

    Why maintainer-level?

    Recent incidents such as xz-utils, event-stream, ua-parser-js and colors were not primarily CVE-driven. Attackers gained control of package maintainership. MaintainerWatch focuses on that layer: publisher changes, release behaviour, maintainer concentration, provenance, advisories, repository practices and package content.

    Explainable by design

    Every score stores its weighted signal values, evidence and an inputs_hash.

    Cross-ecosystem

    One model for npm, PyPI, crates.io, Maven Central and GitHub/GitLab release timelines.

    Impact-aware

    deps.dev dependent counts, downloads and transitive fan-in are reported separately from risk.

    Who is it for?

    MaintainerWatch is a triage and research aid, not an automatic verdict.

    Defenders and maintainers

    Open-source maintainers, application security teams and platform engineers can use it to review dependency changes, maintainer handovers and release behaviour before adoption or upgrades.

    Researchers and policy teams

    Researchers can reproduce the dataset, validation slices and ablations locally. Policy teams can study concentration and hygiene patterns without turning the output into a public target list.

    It is not a malware verdict engine, an automated blocking system or a target list. A high score means “review this”; a low score is not proof of safety.

    Signals

    • publisher_change — maintainer or publisher changed
    • bus_factor — commits concentrated in one author
    • account_age — young maintainer account
    • release_anomaly — dormancy, burst or unusual cadence
    • signing_gap — missing signatures or provenance
    • typosquat — name close to a popular package (homoglyphs and keyboard-adjacent typos)
    • license_inconsistency — missing or conflicting license metadata
    • commit_anomaly — new-author share and commit burst
    • scorecard — low OpenSSF Scorecard score
    • dependency_risk — transitive fan-in and dependency footprint
    • osv_risk — version-aware MAL/CVE advisory
    • depsdev_findings — malicious/deprecated/low-usage findings
    • maintainer_continuity — author handover or newcomer dominance
    • install_script — suspicious npm install/postinstall content

    Quick start

    Install from the checkout, then run one command. The database, exports and report stay local under data/. 

    git clone https://github.com/ovidiurg/maintainerwatch.git
cd maintainerwatch

python -m venv .venv
. .venv/bin/activate
pip install .

# One command: ingest → enrich → score → export → HTML report → CI index
mw main --top 5000 --no-github

    Minimal/offline run: mw main --top 50 --no-github --no-enrich --no-export. Then open data/report.html, or start the read-only API with mw serve --host 127.0.0.1 --port 8000.

    No calibration is needed for installation: the published model is already calibrated. Calibration is a maintainer release activity.

    Scores are risk indicators, not verdicts. A high score means the package deserves review; it does not mean the package is malicious or “attackable”. Medium/high rows in the report include a short risk type, description and next investigation step.

    Validation

    The project publishes a case-control dataset and a reproducible evaluation harness. Current-state metrics are a calibration baseline, not a claim of predictive performance.

    0.891ROC-AUC (v2)
    0.878PR-AUC / average precision
    0.970precision @ threshold 40
    0.010false-positive rate @ 40

    The expanded v2 sample has 489 positives / 1,008 controls. Its 2026 test slice reaches 0.953 AUC and 0.969 precision at threshold 40, while the small pre-2026 train slice remains weak. Pre-incident replay is harder (AUC 0.485): many malicious packages are new at the cutoff. A compromised maintainer account that keeps the same publisher identity can also stay low — ua-parser-js is the documented example, though a maintainer-continuity sensitivity raises it to 40.7 on a very small incident sample. The report includes temporal slices, calibration bins and ablations.

    Safety and responsible use

    Dual-use by nature

    Risk ranking can help defenders triage, but also lowers the cost of offensive reconnaissance. Do not publish ranked target lists or maintainer dossiers. High scores are review candidates, not proof of compromise.

    Isolation boundary

    Static scans never execute package code. Dynamic analysis is delegated to an isolated gVisor/Kata/Docker worker; the analyst process and CI never run untrusted packages.
